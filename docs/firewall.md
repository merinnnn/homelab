## Runtime scope

`scripts/bootstrap/apply-lab-firewall.sh --apply` is the narrow operation. It does not run the rest of network bootstrap. It makes no bridge, interface, sysctl, apt, dnsmasq, service, or boot-configuration changes.

- Defaults: `vmbr1`, `10.0.10.1`, `10.0.10.0/24`, uplink `vmbr0`, protected home prefix `192.168.1.0/24`. All are environment-overridable and must match observed state.
- It inventories nft tables, snapshots only `inet homelab` and `ip homelab_nat`, and constructs a conditional delete/recreate batch for those tables.
- `nft -c -f` must succeed before `nft -f` commits that batch in one transaction. No global ruleset flush occurs; unrelated nft tables are left alone.
- Backups default to `/var/backups/homelab-firewall/<UTC timestamp>.<random>/`. The helper prints the actual directory. It includes project-table snapshots, `apply.nft`, `homelab.nft`, and `rollback.nft`.
- After successful application, the printed rollback command validates then applies `rollback.nft`, restoring prior project tables, including the case where either was originally absent. Do not apply this rollback file before the candidate has successfully created both tables or after unrelated changes to these project-owned tables without reviewing it.

Run only the helper during the narrow live change. Do **not** execute candidate network.sh for this test: that full bootstrap still changes interfaces/sysctls, installs dnsmasq, and restarts services.

## Policy

The project input chain retains established/related responses and allows lab DHCP, DNS to the gateway address, and IPv4 ICMP to the gateway. Other new lab-to-host traffic, including SSH and Proxmox web management, drops. Trusted main-interface management is unaffected by this project's input chain; independent firewall tables can impose additional restrictions.

The forward chain first drops lab traffic destined for the protected home prefix. It allows correctly sourced IPv4 lab traffic to the uplink and established/related IPv4 return traffic to the lab. All other traffic routed into or out of the lab bridge drops. Unrelated forwarding does not change. NAT remains IPv4 masquerade from the lab subnet through the uplink.

This closes the confirmed one-way ingress gap: new main-LAN packets must be dropped before they reach a lab guest. A failed TCP handshake alone is insufficient evidence, because the previous policy could deliver the request while dropping its response. Compare packet arrival at the guest before and after application.

Only the supplied `MAIN_NET` is protected from outbound lab access. This does not claim to block every RFC1918/VPN/internal routed prefix. Same-bridge guest-to-guest traffic and traffic generated by the Proxmox host are outside this routed-forwarding boundary. Existing host-input established sessions are retained. No conntrack flush is performed.

IPv6 forwarding was reported disabled on the live nodes. The candidate's final lab-interface drops also cover forwarded IPv6 packets, but IPv6 routing was not exercised. Do not report live IPv6 isolation or support as tested.

## Persistence is a separate reviewed migration

Runtime application does **not** change the existing `/etc/nftables.conf`. If that file still contains the legacy global `flush ruleset` and old project rules, a reboot or future load can erase unrelated rules and restore the ingress gap. Appending a new include to that file does not fix its global flush. Candidate network.sh therefore prominently reports that firewall persistence remains pending.

`configs/proxmox/homelab.nft` is the dedicated managed-file candidate for `/etc/nftables.d/homelab.nft`. It uses `destroy table` for only the two project tables before declaring them again. This supports a fresh boot and repeated reload without duplicates, while leaving unrelated tables untouched. The [official nft manual](https://netfilter.org/projects/nftables/manpage.html) documents `destroy` as tolerating absent tables; the exact live node must still accept the file with `nft -c` before installation.

The companion `configs/proxmox/nftables-include.conf` contains only the dedicated include. It may replace `/etc/nftables.conf` **only after review confirms the old file contains solely the legacy project-generated header, global flush, and the two project tables**. Back up the old file first. If there are unrelated declarations/includes, preserve them and prepare a reviewed merged candidate instead. Do not mechanically remove arbitrary nft blocks or replace an unknown configuration.

Coordinator persistence sequence:

1. Back up `/etc/nftables.conf` and any existing managed file; retain the helper's runtime rollback directory.
2. Confirm legacy ownership and inspect existing included files/service unit behavior. Prepare the final top-level configuration preserving unrelated content and removing the old project's global flush and declarations.
3. Stage the dedicated persistent file, then run `nft -c -f` against that file and the proposed top-level configuration with its final include resolved. Stop if either validation fails. Do not ignore parser/version errors.
4. Install the two reviewed files with appropriate root ownership and atomic file replacement. Validate the installed top-level file again. Use `nft -f /etc/nftables.conf` to exercise this scoped configuration when approved; avoid an unreviewed `systemctl restart nftables`, whose service stop action may flush the global ruleset.
5. Compare unrelated nft tables before/after, confirm project rules, repeat the same load to check no duplication, and rerun gateway/DHCP/DNS/internet, ingress-denial, home-denial, and management-access tests. Verify the existing boot activation mechanism references this configuration. Node reboot remains a separate availability-affecting test.

Rollback of a persistent migration requires restoring the backed-up files **and** reviewing which runtime rules should be restored; a disk-file restore alone does not alter the currently running kernel rules. Restoring the known old legacy file also restores its documented flaws, so do not present that as a durable solution.
