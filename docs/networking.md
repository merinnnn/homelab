## Bridges

Each node has:

- `vmbr0`: management/home LAN, bridged to physical `eno1`.
- `vmbr1`: internal bridge without physical ports, gateway `10.0.10.1/24`.
- dnsmasq on vmbr1, DHCP `10.0.10.100`–`10.0.10.200`, gateway/DNS `10.0.10.1`.
- IPv4 forwarding and masquerade through vmbr0. IPv6 forwarding was disabled when inspected.

The two vmbr1 bridges are **separate networks**. Reusing the same addresses on both nodes does not provide cross-node connectivity or migration networking. Any future inter-host lab transport needs an explicit design.

## Routed isolation

Project rules are held in `inet homelab` and `ip homelab_nat`. The helper replaces those tables atomically after parser validation and preserves other tables. It does not globally flush the ruleset.

Lab guests may use the gateway for DHCP, DNS and IPv4 ICMP and may initiate correctly sourced IPv4 traffic to the uplink except the protected home prefix. Established internet replies may return. Other new traffic to host management or routed into the lab drops. This is a routed boundary; same-bridge guest traffic and traffic generated by the host itself are outside it. The configured protected prefix is `192.168.1.0/24`, not every possible private/VPN network.

The former rule set accepted inbound home-to-lab packets while blocking their replies. Packet capture demonstrated that a failed ping could still reach a guest. After correction, captures on both lab bridges received zero matching packets during explicit routed home-LAN probes. Guests retained gateway, DNS, internet and HTTPS connectivity; tested host SSH/API connections from guests timed out.

See [firewall maintenance](firewall.md) before changing host rules. The full network bootstrap applies runtime rules but deliberately leaves boot integration for review; it must not overwrite an unknown existing firewall configuration. Do not run `systemctl restart nftables` blindly: the service stop action may globally flush rules.
